# Generated bindings

Kotlin and Swift bindings for `lc-wallet-ffi`, generated by uniffi and
committed so the host-language API is reviewable without a Rust
toolchain. Do not edit by hand — regenerate after any change to
`lc-wallet-ffi/src/lib.rs`:

```
cargo build -p lc-wallet-ffi
cargo run -p lc-wallet-ffi --features cli --bin uniffi-bindgen -- \
  generate --library target/debug/liblc_wallet_ffi.so --language kotlin --out-dir bindings/kotlin
cargo run -p lc-wallet-ffi --features cli --bin uniffi-bindgen -- \
  generate --library target/debug/liblc_wallet_ffi.so --language swift --out-dir bindings/swift
```

The host app links the bindings against the compiled library:

- **Android**: build `lc-wallet-ffi` as a `cdylib` per ABI with
  `cargo-ndk` (arm64-v8a, armeabi-v7a, x86_64), ship the `.so` files in
  `jniLibs`, drop `bindings/kotlin` into the source set, and add
  `net.java.dev.jna:jna` — uniffi's Kotlin runtime loads the library via
  JNA.
- **iOS**: build `staticlib` for `aarch64-apple-ios` (+ simulator),
  wrap in an XCFramework with `lc_wallet_ffiFFI.h` and the modulemap,
  and add `lc_wallet_ffi.swift` to the target.

Cross-compiled artifacts are not produced in this repo yet — this host
has no NDK or Xcode. The bindings themselves and the host-side API are
final; producing per-platform binaries is CI work, tracked in the SDK
decision doc.

Host-side contract, in one paragraph: construct `LiquidConnectWallet`
with the master blinding key, network, a persisted install id, and a
`WalletEventListener`; events arrive on a background thread. Feed
scanned QR payloads to `openLink`. Render `SignRequested` with
`summarizePset` — and when `fullyExplicit` is false, your own decode
must fill the gaps before anyone approves. Sign with your own signer and
deliver via `acceptSign`. The SDK never holds keys and never signs.
